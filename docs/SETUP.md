# Connect Hermes Keys to an agent

Hermes Keys types offline by default. **Agent** and **Acts** make a request only after you review a prompt and tap **Send prompt**. They currently require an HTTPS, bearer-authenticated **Hermes Agent OpenAI-compatible API**. The settings connection diagnostic separately requires confirmation before sending its fixed synthetic prompt. The keyboard has no bundled server, model, or account. Android 6+ is required for the encrypted Agent configuration; normal keyboard features support the app's lower Android minimum.

## Fast path: your own home server

1. Install [Hermes Agent](https://hermes-agent.nousresearch.com/docs/) on a computer you control. Create a **new, un-cloned profile** for the keyboard, e.g. `hermes profile create keyboard`. Configure a model in that profile with `hermes -p keyboard model`, then check `hermes -p keyboard chat -q 'Reply exactly READY'`. A subscription or remote API model still sends inference to its provider; for fully local inference, configure a supported local model server in that profile. The Android app itself does not log in to model providers.
2. Restrict the keyboard profile **before exposing it**. Set `hermes -p keyboard config set platform_toolsets.api_server '[]'` for no tools (or explicitly allow only a narrow toolset such as web search if you need it). Set a small turn budget, e.g. `hermes -p keyboard config set agent.max_turns 4`, and confirm the served `/v1/toolsets` contains no terminal, file, code-execution, browser, connector, delegation or scheduled-job tools. A profile is configuration isolation, **not** an OS sandbox: for stronger separation run it under a restricted OS user/container. Never point a keyboard at your main terminal-capable agent. Previewing the *result* cannot stop server-side tools that ran earlier.
3. Set up the [API server](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server) for that profile. In its **private**, mode-600 `.env` (not the repository), set `API_SERVER_ENABLED=true`, `API_SERVER_HOST=127.0.0.1`, an unused `API_SERVER_PORT` (for example `8643`), and a unique high-entropy `API_SERVER_KEY`. Create/store the key with a password manager; do not put it in screenshots, logs, chat, issue reports or a URL. Start `hermes -p keyboard gateway` and arrange a supervised startup for daily use. On the server, the authenticated `/v1/models` route should work while the same route without the key returns 401. A successful CLI chat alone does **not** prove the phone-facing route is configured correctly.
4. Give the phone an Android-trusted **HTTPS** route to this loopback listener. The simplest private option is [Tailscale Serve](https://tailscale.com/kb/1312/serve): install Tailscale on server and phone in the same tailnet, inspect `tailscale serve status` for existing routes, then serve the dedicated loopback port on an unused HTTPS port, for example `tailscale serve --bg --https=9444 http://127.0.0.1:8643`. Use **Serve**, not public Funnel. Confirm the URL works over mobile data as well as home Wi-Fi. A VPS can host this same restricted profile inside a private tailnet, but it is optional; it is not needed between phone and home server. Tailscale can use relays/control-plane services, so a tailnet is not a promise of entirely serverless transport.
5. On Android, open **Hermes Keys Settings → Hermes agent settings**. Enter the HTTPS **server root**, for example `https://your-host.your-tailnet.ts.net:9444` (not `/v1` or `/v1/chat/completions`), paste that profile's API-server bearer key, check **Allow explicit Agent requests to this server**, and tap **Save configuration**. For a multiplexed Hermes gateway, the root may instead end in `/p/keyboard`; use that profile's key. `localhost` on the phone means the phone, not your server. The app rejects HTTP and untrusted certificates. The signed release uses a different application ID from the earlier `.debug` build; encrypted settings and Acts do not migrate automatically. Configure the release separately, and export/import individual Acts only by explicit choice.
6. In Agent settings, tap **Test saved connection**, review the consent message, then explicitly confirm **Send one saved-connection test**. It uses only the saved URL, token and enabled opt-in—not unsaved form edits—and sends exactly `Reply exactly READY.` through the same completion route as Agent. Opening settings or saving never sends a request. No editor/clipboard text or Acts are read; the response is discarded, never displayed or inserted. Success means a valid final text response, not verified profile identity, tool safety or exact `READY` content. Each confirmed test may incur cost/retention; there are no retries. Cancel before confirmation sends nothing. After sending, Close, unchecking opt-in, Save, Forget or activity destruction cancels locally; the 45-second UI deadline may cancel sooner than a slow server finishes. Server work may continue after cancellation/timeout, so a fresh confirmed test may incur another cost.
7. To check the separate keyboard review/insertion flow, use **non-sensitive synthetic text** in an ordinary editable field: type `Reply exactly READY`, expand the keyboard toolbar, tap **Agent**, check the exact text and HTTPS destination, then tap **Send prompt**. Inspect the returned answer; **Insert after selection** is a separate action and keeps the original text. You can also choose **Acts** from the toolbar or enable the optional hold-Space Action popup in Advanced settings. Ordinary typing must not contact the server.

## If it does not answer

| What you see | Check first |
|---|---|
| No Agent action / setup required | Expand the toolbar; ensure the Agent button is enabled in Toolbar settings and the app opt-in is checked. |
| Request refused before preview | Use a regular text field, not a password, incognito or no-personalized-learning field. Unlock the phone and keep the same editor/selection open. |
| Connection or request failed | Use **Test saved connection** for fixed local categories: DNS/network → phone VPN/tailnet/connectivity; TLS → Android-trusted certificate; 401/403 → saved key/permissions; 404 → server-root/profile/proxy path; 429 → quota/rate limit; 5xx → gateway/provider; timeout → network/model availability. Other HTTP statuses/redirects are refused without following them. Raw exception/server text is never shown. The ordinary keyboard flow retains its generic error. |
| Diagnostic or editor Agent busy after cancellation/timeout | Each flow has a separate process-wide slot with no queue, held until its request and transport cleanup return. Wait for cleanup; if transport is uncooperative, force-stop this app (no data clearing needed). Force-stop does not guarantee server work stops. No automatic retry; once free, a new test or editor request still needs fresh confirmation. |
| Preview appears but no response | Only **Send prompt** starts a request. Check profile provider/model availability and usage limits on the server. The app accepts a final `finish_reason: stop` text answer, not a tool-only, cancelled or truncated result. |
| No insertion | Review the answer and tap **Insert after selection**; changing focus/selection invalidates the flow. Never assume retrying is free: server work might continue after local cancellation. |

**Do not post tokens, private prompts or raw settings screenshots in public issues.** To reset a compromised connection, use **Disable and forget** in the app *and* revoke/rotate the API-server key on your server. App uninstall/clearing data removes its encrypted configuration and local Acts. The diagnostic completed one synthetic live test on an API 34 phone. The signed release completed fresh-install/onboarding and no-configuration checks, but its authenticated Agent route and failure paths still need device testing. Guided pairing remains planned.

## Scope of current backend support

The shipped client sends one non-streaming OpenAI-style `/v1/chat/completions` request with model alias `hermes-agent`; it is **not yet a generic Codex, Claude Code or Grok client**. Hermes on your server can itself use its supported model providers, including host-side Codex subscription OAuth where authorized, xAI or API-key providers, and a configured local model. Keep provider credentials on the server. Other agent harnesses would need a compatible, restricted host-side adapter and explicit verification; do not paste a subscription OAuth token into the keyboard.
